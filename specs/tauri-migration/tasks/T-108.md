## Goal
The remaining `window:` utility channels and both `dialog:` channels are
implemented in Rust with v1 semantics: guarded `open-external` with the WSL
interop fallback, fullscreen/reload/devtools toggles, and the two file-open
dialogs (content-reading and path-only).

## Acceptance criteria
- [ ] 1. `window:open-external`: accepts only `^https?://`-matching strings
      (v1 rejects everything else silently — same here: no error, no open);
      opens via `tauri-plugin-opener`. **WSL behavior preserved**: on Linux
      with `/microsoft/i` in the kernel release, spawn
      `cmd.exe /c start "" <url>` (no shell interpolation — arg-vector
      spawn exactly like v1's `execFile`), falling back to the normal
      opener if interop fails.
- [ ] 2. `window:toggle-fullscreen` flips the calling window's fullscreen
      state and **returns the new bool** (v1 contract); `window:reload`
      reloads the webview; `window:toggle-devtools` toggles devtools —
      built with the devtools feature enabled so it works in release
      builds like v1 (the menu items are devOnly, the channel is not).
- [ ] 3. `dialog:open-file` (via `tauri-plugin-dialog`): applies v1
      defaults — title "Open File", filters default All Files — and
      returns `{ cancelled: true }` on cancel, else `{ filePath:
      <basename only>, content: <utf-8 file content> }` (yes, basename —
      v1 strips the directory; parity, not taste).
- [ ] 4. `dialog:open-file-path`: title default "Select File", returns
      `{ cancelled: true }` or `{ filePath: <full path> }`. Both handlers'
      response shapes get contract fixtures under the T-103 framework
      (cancelled and success variants).
- [ ] 5. Plugin registration + capability entries
      (`src-tauri/capabilities/`) are scoped to what these channels need —
      `opener:allow-*` permissions restricted to opening URLs (no
      allow-open-path), plus the dialog permissions; dispatch arms replace
      their stubs; burndown flips
      `window:open-external`, `window:toggle-fullscreen`, `window:reload`,
      `window:toggle-devtools`, `dialog:open-file`,
      `dialog:open-file-path` to `migrated`.
- [ ] 6. Unit tests cover the URL guard (rejects `file://`, `javascript:`,
      non-strings) and the WSL detection predicate (parameterized on a
      release-string input, not the live kernel).

## Notes
- Open-external uses `tauri-plugin-opener` (2.5.x — the `shell.open` API
  split into opener, versions-baseline). **Do not add
  `tauri-plugin-shell`**: it is only for child processes/sidecars, which
  this task has none of (the WSL fallback spawns `cmd.exe` via
  `std::process::Command` directly).
- The URL guard is a security boundary (v1 comment: "never file:// or app:
  schemes from the renderer") — reviewers should attack it; keep the regex
  anchored and case-insensitive like v1's `/^https?:\/\//i`.
- Dialog handlers must not block the async runtime — use the plugin's async
  API or `spawn_blocking` for the file read; the file read failing (EACCES,
  binary data) should reject with a message, matching v1's thrown `fs`
  error behavior.
- Live open-external/devtools behavior is exercised in T-199's manual
  checklist; this task's tests cover logic, not OS side effects.
- Registering plugins touches `main.rs` conceptually — if a code change
  there is unavoidable, coordinate with the orchestrator (T-105/T-106 also
  touch it); prefer plugin init via the builder in a function this task
  owns.
