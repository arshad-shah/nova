## Goal
The v1 capability/permission model ports as data + pure decision logic: the
six permission ids, the consent metadata, the effective-grants intersection,
and the grants persistence location — so a migrated v1 config keeps its
grants and the consent UI renders unchanged. Enforcement surfaces shrink to
what declarative plugins can actually reach (ADR-0003 closes the advisory
hole structurally).

## Acceptance criteria
- [ ] 1. Permission ids ported exactly: enforced `keyring|connections|ipc`,
      advisory `network|filesystem|process`; `PERMISSION_INFO` metadata
      (title, description, enforced, sensitive) matches v1 string-for-string
      so `plugins:get-permissions` renders the identical consent UI.
- [ ] 2. `effective_grants(declared, user_granted) = user_granted ∩ declared`
      with set semantics: unknown/duplicate values dropped, a stale grant for
      an undeclared capability never survives. Unit tests cover: empty
      declared, empty granted, stale grant, full overlap; plus a property
      test that the result ⊆ declared always holds.
- [ ] 3. Trusted semantics parity: bundled (compiled-in) plugins report
      `trusted: true`, `granted == declared`, and `set_grants` on them is a
      no-op returning the declared set; third-party grants default to empty
      (deny-by-default).
- [ ] 4. `set_grants(name, permissions)` intersects with the manifest's
      declared set, persists, and returns the effective set — the
      `plugins:set-permissions` reply shape `{ granted }` is unchanged.
- [ ] 5. Grants persist in the exact v1 config-store location/keys (read the
      `pluginGrantsStore` wiring in src/main/ipc-handlers.ts and pin it), so
      a config.json migrated by verql-migrate-v1 (T-209) yields the same
      grants with **zero** re-consent; a fixture v1 config proves it.
- [ ] 6. The disabled-plugins persistence (`disabledPluginsStore` semantics —
      isDisabled/markDisabled/markEnabled, persisted only for user-initiated
      deactivation) ports alongside, same config location, same fixture test.
- [ ] 7. `PermissionDeniedError` equivalent exists with the v1 actionable
      message shape (names the plugin, the permission, and the fix) for any
      future capability call path; since declarative plugins execute no code,
      a test documents that no v2 code path can reach an enforced-capability
      call from third-party input (the guard exists for the ADR-0003 WASM
      horizon, not dead code pretending to enforce).

## Notes
- v1's honest posture (permissions.ts header): advisory permissions were
  *never* enforceable in-process. ADR-0003 makes the model strictly stronger
  — say so in rustdoc, don't copy the JS caveats verbatim.
- The intersection lives in ONE place in v1 (`effectiveGrants`) and is called
  from `grantsFor`, `getPermissionState`, and `setGrants` — keep that
  single-implementation shape; the adversarial reviewer will look for a
  second hand-rolled intersection.
- Consent strings are user-facing: route them through the i18n key convention
  if backend-originated strings must arrive as keys (02-target §what stays
  TypeScript); coordinate with the renderer's existing consent UI rather
  than inventing new copy.
- T-407 exposes this via `plugins:get-permissions`/`set-permissions`; keep the
  API surface it needs stable.
