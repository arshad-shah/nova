# T-311: Export/import glue (`export:*`, `import:*`, dialogs; formats may stub)

- status: open
- phase: 3
- depends_on: [T-302]

- risk: medium
- estimate: M
- verify.scope: rust, contract, e2e

## Goal
The six `export:*`/`import:*` channels exist with v1 glue semantics —
format-registry resolution, driver-provided data reads, save/open dialogs,
filename sanitization, and the filesystem write path — proven end-to-end
with a clearly-marked temporary passthrough JSON exporter. Real formats
arrive in Phase 4 (T-402); importer channels may return `NOT_MIGRATED`
until then.

## Acceptance criteria
- [ ] 1. A provisional exporter/importer registry seam exists in
      `verql-core/src/registries/formats.rs` mirroring the v1 SDK
      registries' resolution rules: `list(connectionType)` ordering,
      `resolve(format, connectionType)` with connection-type-specific
      registrations winning over generic, first-registration-wins per
      format in the dedupe. Marked provisional for T-401 to extend (not
      rewrite) — the trait shapes are reviewed against
      `exporter-registry.ts`/`importer-registry.ts`.
- [ ] 2. `export:formats-list` / `import:formats-list` return
      `ExportFormatInfo` / `ImportFormatInfo` shapes (format, displayName,
      extension(s), supportsSchema / driverExecutes booleans) deduped
      first-wins per format, resolved for the profile's connection type.
- [ ] 3. `export:table` parity: resolves the exporter (error `No exporter
      registered for format '<f>' on '<type>' connections`), reads rows via
      the *driver's* `get_table_data` (error `Driver '<type>' does not
      implement getTableData(). …` when absent; `Not connected` without an
      adapter), executes the exporter with `{ tableName, schema,
      connectionType, includeSchema }`, opens a save dialog
      (tauri-plugin-dialog) defaulting to
      `<sanitized-table>.<extension>` with the exporter's display-name
      filter, returns `{ cancelled: true }` on cancel, writes the content
      and returns `{ filePath }` on confirm.
- [ ] 4. Filename sanitization ports `safeFileName`: strip control chars,
      `<>:"/\|?*`, cap at 200 chars, fall back to `export` — pinned by
      tests incl. a path-traversal attempt (`../../etc/passwd`).
- [ ] 5. `export:query-result` parity: resolves with empty connection type,
      synthesizes `SchemaColumn`s from field names (dataType `unknown`,
      nullable true), exports as table name `query-result`, same
      dialog/write/cancel flow.
- [ ] 6. Temporary passthrough JSON exporter: registered as format `json`
      (extension `json`), serializing rows to pretty-printed JSON — marked
      `TEMPORARY(T-402)` in code and in the burndown notes; the e2e case
      exports a seeded table through the full dialog+write path and
      validates the file exists with the expected row count. It must be
      trivially removable when T-402 lands (single registration site).
- [ ] 7. `import:csv` / `import:sql`: the open-dialog + file-read glue and
      the handler skeletons exist with v1 flow (open dialog → cancelled
      short-circuit → `findByExtension` resolution → parse →
      driverExecutes branch vs generic CSV-into-table using the driver's
      `quoteChar`+`placeholderStyle`, with the v1 error messages when
      those capabilities are missing); until a real importer registers
      (T-402) the post-dialog path returns the distinctive `NOT_MIGRATED`
      error and the burndown table records both channels as
      stub-after-dialog.
- [ ] 8. Contract fixtures for all six channels round-trip (cancel shapes,
      format-info lists, export result shapes).

## Notes
- Dialogs must be injectable (trait over tauri-plugin-dialog) so handler
  tests and the e2e script can drive confirm/cancel without a real window;
  the v1 flow's `{ cancelled: true }` returns (not throws) are contract.
- The generic CSV-into-table fallback (`csv-into-table.ts`) is glue, not
  format logic — port its skeleton here or in T-402, but the *decision* of
  where must be logged; its no-dialect-branches rule
  (`export-import-no-hardcoding`) applies either way.
- v1 writes exports synchronously on the main thread; v2 must write off
  the async runtime (spawn_blocking) — unobservable difference, fine.
- Coordination: six dispatch-table lines in
  `src-tauri/crates/verql-ipc/src/dispatch.rs` (shared file);
  `verql-core/src/registries/` is ground T-401 will build on — leave a
  module-level doc comment stating the T-401 handoff contract.
