## Goal
Plugin install from a directory or a zip archive works with the v1 guard
set intact — but via the `zip` crate instead of shelling to `unzip` — and
uninstall removes exactly the installed directory. All v1 attack fixtures are
rejected before anything lands in the trusted plugins directory.

## Acceptance criteria
- [ ] 1. `install_from_zip`: extracts with the `zip` crate (no
      `std::process::Command`); entry names are checked **before extraction**
      with the `assertSafeArchivePaths` rules ported exactly — trim, skip
      empties, reject absolute paths, reject Windows drive-letter prefixes
      (`^[a-zA-Z]:`), reject any `..` segment split on both `/` and `\`.
- [ ] 2. Extraction goes to a fresh, unpredictable, owner-only (0700) temp dir
      (`tempfile::tempdir` — the v1 `mkdtempSync` rationale: a predictable
      path lets a local attacker pre-plant content). Temp dir removed on all
      paths (success and failure).
- [ ] 3. Single-top-level-directory unwrap parity: exactly one subdirectory in
      the extracted tree → install from it; otherwise install from the root.
- [ ] 4. `install_from_path` ordering parity — nothing is copied until every
      check passes: (a) manifest parsed (plugin-manifest.json, else
      package.json form); (b) name matches `^[a-z0-9-]+$` (destination-path
      defense: the name becomes a path segment); (c) **full** manifest
      validation (T-404) — a bad version/permission/field never reaches disk;
      (d) bundled-name collision refused ("Cannot install: '<name>' is a
      bundled plugin name"); (e) symlink walker finds no symlink anywhere in
      the source tree ("Refusing to install: contains a symlink (<path>)").
- [ ] 5. Destination `<appData>/plugins/<name>` is replaced atomically-enough
      (existing dir removed, source copied recursively); result shape parity:
      `{ success, name?, error? }`.
- [ ] 6. v2 twist per ADR-0003: an archive classified IncompatibleJs (T-404)
      is refused at install time with an error citing v2's
      declarative-only support — it must NOT be written to disk and later
      fail to load.
- [ ] 7. Attack-fixture tests (committed under the crate's tests/):
      zip-slip (`../../evil.txt`), absolute-path entry, drive-letter entry,
      symlink inside the archive/source tree, bundled-name-collision
      manifest, name with path separators (`../evil`) — each returns
      `success:false` with the pinned error AND a filesystem assertion proves
      zero bytes were written outside the temp dir and plugins dir.
- [ ] 8. `uninstall`: refuses bundled names with an error, removes the plugin
      directory recursively, forgets the entry; idempotent for unknown names.

## Notes
- v1 relied on `unzip` stripping traversal *plus* the explicit pre-check as
  defense-in-depth. The `zip` crate's `enclosed_name()` gives similar
  stripping, but the explicit ported check is the contract — do not rely on
  crate behavior alone; test both layers.
- Symlink handling in zip archives: v1's post-extraction `findSymlink` walk
  catches symlinks unzip recreated. With the `zip` crate, refuse symlink
  entries at extraction time (unix mode bits) AND keep the walk — both.
- v1 bug-for-bug note: `installFromPath` re-parses the manifest after copy
  and only then registers state; keep the "registered as discovered, not
  activated" post-install state — activation is an explicit T-407 call.
- The lifecycle broadcasts (`plugins:lifecycle` installed/uninstalled) are
  wired in T-407, not here — keep install/uninstall pure of event emission.
