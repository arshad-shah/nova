## Goal
`verql-tools` provides the shared ToolRegistry (one registration → both AI and
MCP surfaces, gated by `surfaces`) and the canonical db-tools set with
identical ids, JSON schemas, permissions, and result shapes, plus the shared
write-detection helpers both consumers use.

## Acceptance criteria
- [ ] 1. Registry parity with tool-registry.ts: **flat id space,
      last-wins replace** on duplicate id (no error — deliberate, ids are the
      literal LLM/MCP names); unregister; list; `get_tool_definitions()` →
      `{name, description, parameters}`; onChange listeners; an activity
      recorder hook invoked after every `execute` (success flag, durationMs,
      error message on throw) feeding the unified activity log.
- [ ] 2. Tools ported with identical id/name/description/permission:
      `query` (write), `explain_query` (read, runs `EXPLAIN <sql>`),
      `list_tables` (read), `describe_table` (read), `get_schemas` (read),
      `connection_info` (read), `get_app_activity` (read; kinds enum
      `query|tool-call|connection|notification|network`, limit default 50,
      cap 500, most recent first).
- [ ] 3. Input schemas match v1's zod→JSON-Schema output field-for-field
      (fixture per tool diffed against a captured v1
      `getToolDefinitions()` dump) — property names, types, required arrays,
      descriptions.
- [ ] 4. Result shapes pinned: no-connection sentinel `{success:false,
      data:null, display:'No active database connection in Verql'}` for every
      db tool; `query` data = `{rows (sliced to a live max-rows getter),
      rowCount, fields:[{name,dataType}], duration, affectedRows}` and
      display `Query returned N row(s)`; `describe_table` data
      `{columns, indexes}`; `get_schemas` data `{schemas, databases}` with
      per-call error swallowing to `[]` (v1 `.catch(() => [])`).
- [ ] 5. Cancellation parity: a tool call carries an abort handle; abort
      mid-query triggers `cancel_query` on the connection and the call
      settles as a 'Cancelled' error (tools.ts `withCancellation`).
- [ ] 6. `surfaces` gating carried on the Tool type (`None` = all surfaces;
      `['ai']` tools must be invisible to MCP's exposed set — asserted here
      with a unit test against the selection helper, enforced end-to-end in
      T-506).
- [ ] 7. Write detection ported exactly from tool-schema.ts as the **single
      shared implementation** for AI (T-504) and MCP (T-507):
      `is_write_query` — comment stripping (`/* */`, `--`) then word-boundary
      case-insensitive match on
      INSERT|UPDATE|DELETE|DROP|ALTER|CREATE|TRUNCATE|REPLACE|MERGE|GRANT|REVOKE
      anywhere in the string; `is_write_tool_call(effective_permission,
      params)` — write permission, or a read tool whose `sql` param is a
      write. Tests include: `SELECT 1; DROP t`, write hidden in a comment
      must NOT mask detection, table named `delete_log` trips it (accepted
      false positive — documented), `EXPLAIN ANALYZE DELETE …` trips it.
- [ ] 8. Max-rows getter is read per call (tracks the live setting without
      re-registering tools) — test flips the setting between calls.

## Notes
- The keyword set in `is_write_query` is a security surface: tightening or
  loosening it is a deliberate change requiring review, never a port
  side-effect (tool-schema.ts header says exactly this).
- `db-tools` was the one "essential" v1 plugin; per ADR-0002 that machinery
  disappears — the tools are compiled in and always present.
- MCP registers tools by id with the description as the LLM-visible surface;
  changing any description string breaks stream-replay fixtures in T-503/T-599
  (system prompts/tool defs feed token budgets). Byte-stable strings.
- Coordination: `src-tauri/Cargo.toml` gains one member line; T-503/T-506
  consume this crate's API — keep `execute` signature stable once they start.
