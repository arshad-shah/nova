## Goal
`tests/parity/` exists: a harness that drives the same operation through
either stack and diffs serialized results against committed golden JSON. This
task builds the skeleton, the **v1 (Electron) driver** that generates goldens
headlessly, and proves it end-to-end with at least one SQLite case. The Rust
driver plugs into the same runner later (Phase 1+); every driver/config/
export task from Phase 2 on lists its parity cases against this harness.

## Acceptance criteria
- [ ] 1. Directory layout: `tests/parity/{golden,cases,allowlists,runner}`
      plus `tests/parity/README.md` documenting the case format, the runner
      CLI, and the golden-regeneration rule (goldens come only from v1 on
      `main`; never hand-edited; never regenerated by the task that makes
      them pass).
- [ ] 2. A case is a JSON file under `cases/`: id, required fixture (e.g.
      `sqlite-testdb`, `docker-postgres`), a sequence of IPC-level
      operations (channel + args, using the v1 wire strings), and which
      results are asserted. The runner is stack-agnostic: it takes
      `--stack v1|v2` and resolves a backend adapter implementing one
      `invoke(channel, args)` call — the exact seam both stacks share.
- [ ] 3. The v1 backend drives the real Electron main-process handlers
      headlessly (no window): via `electron` launched with a harness entry
      that calls `registerIpcHandlers()` and services invokes, or an
      equivalent script entry. It must exercise the *real* handler code in
      `src/main/ipc/**` — reimplementing handler logic in the harness is a
      rejection.
- [ ] 4. Per-case allowlists under `allowlists/` name fields permitted to
      differ (e.g. `durationMs`), applied during diff; no global allowlist
      exists (per `verification.md`).
- [ ] 5. End-to-end proof: a case `sqlite/select-basic` runs a SELECT with
      params against `docker/testdb.sqlite` through the v1 stack; its
      golden (columns, rows, rowCount — QueryResult shape) is committed
      under `golden/`, and replaying with `--check` passes; corrupting one
      golden value makes `--check` fail (evidence in Log).
- [ ] 6. Runner modes: `--generate` (v1 only, writes goldens) and `--check`
      (diffs, exit code 0/1, prints a field-level diff on failure).

## Verify
```bash
# setup: build the seeded sqlite fixture (uses docker):
bash scripts/make-sqlite-testdb.sh
node tests/parity/runner/run.mjs --stack v1 --case sqlite/select-basic --check
test -d tests/parity/golden && test -d tests/parity/allowlists
test -f tests/parity/README.md
```

## Notes
- Headless Electron on CI/Linux needs a virtual display (`xvfb-run`) or
  `electron --no-sandbox` care — document what the runner needs; if the
  harness entry avoids creating a BrowserWindow, most of this pain vanishes
  (`registerIpcHandlers()` in `src/main/ipc-handlers.ts` does not require a
  window, but `app.getPath('userData')` requires `app.whenReady()` —
  point userData at a temp dir so harness runs never touch real user data).
- `ipcMain.handle` needs an invoke *sender*; simplest is to bypass ipcMain
  and call the registered handlers through a harness-provided `handle`
  implementation injected at the `ipc/context.ts` seam — that still runs
  real handler code (criterion 3) without faking WebContents. Keep any such
  seam in `tests/parity/`, not in `src/main/` (v1 is read-only reference).
- The runner file names used in Verify are binding once merged — T-099 and
  every later gate call them verbatim.
