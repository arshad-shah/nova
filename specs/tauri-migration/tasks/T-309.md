## Goal
`verql-ssh-tunnel` implements the connection-middleware contract on russh:
when a profile carries `sshHost`, `before_connect` opens an SSH session,
forwards a loopback listener to the target host/port, and returns the
profile rewritten to `127.0.0.1:<localPort>`; `on_disconnect` tears the
tunnel down. Contributes the five `ssh*` connection fields. Verified
end-to-end against an sshd container fronting the seeded Postgres.

## Acceptance criteria
- [ ] 1. `should_apply` is exactly "profile has a non-empty `sshHost`".
      Field semantics match v1: `sshPort` default 22, `sshUser` default
      `root`, auth prefers `sshPrivateKey` (the field carries **key
      content**, v1 type `file`) over `sshPassword`; target defaults
      `host: localhost`, `port: 5432` when the profile omits them.
- [ ] 2. `before_connect` establishes the SSH session, binds a listener on
      `127.0.0.1` on an OS-assigned free port, forwards accepted
      connections through `direct-tcpip` channels to the remote host/port
      (bidirectional pipe), registers the tunnel under the profile id, and
      resolves to `{ ...profile, host: "127.0.0.1", port: <localPort> }`.
      Multiple concurrent client connections through one tunnel work
      (connection pools open several sockets — v1's single net.Server
      accepted many).
- [ ] 3. Error-message parity, matched by classification tests: auth
      failures → `SSH authentication failed — check credentials or private
      key`; TCP-refused to the SSH host → `Cannot reach SSH host
      <host>:<port>`; anything else → `Failed to establish SSH tunnel:
      <detail>`.
- [ ] 4. Teardown: `on_disconnect(profileId)` closes the listener and the
      SSH session and removes the registry entry (idempotent for unknown
      ids); crate shutdown (v1 `deactivate`) closes every active tunnel.
      No leaked sockets/tasks after disconnect (asserted via the e2e
      scenario + a tokio-task count check).
- [ ] 5. Registration: the middleware registers with T-301's
      ConnectionManager middleware hook; the five connection fields
      (`sshHost` text, `sshPort` number default 22, `sshUser` text,
      `sshPassword` **password type** — keyring-handled via the T-203
      secret-field seam, `sshPrivateKey` file, all `group: "ssh"`)
      serialize identically to v1's manifest contribution.
- [ ] 6. docker-compose gains an `sshd` service (e.g. `linuxserver/openssh-
      server` or a small Dockerfile under `docker/sshd/`) on the compose
      network with password + key auth enabled and documented creds in
      `docker/README.md`; `scripts/test-dbs.sh up` starts it with the rest.
- [ ] 7. E2E parity case: a Postgres profile with `sshHost` pointing at the
      sshd container (Postgres reachable only via the container network)
      connects through the tunnel, runs a query, disconnects, and the
      tunnel closes — plus the auth-fail and unreachable-host error cases
      asserting criterion 3 messages.

## Notes
- v1 quirk not worth porting: it picks a free port by bind-close-rebind
  (racy) and calls `forwardOut` once before the server exists. Bind the
  listener directly and open a channel per accepted connection — the
  *observable* contract (loopback host/port rewrite, error messages,
  teardown) is the parity surface, not the socket choreography. Record
  this as an allowed internal difference in the case allowlist.
- `sshPrivateKey` holds the key material itself (v1 passes it straight to
  ssh2 `privateKey`) — do not treat it as a path. Passphrase-protected
  keys were unsupported in v1; keep that (log as a feature idea).
- Host-key verification: ssh2 in v1 does not verify host keys by default —
  match that behavior for parity and log the hardening idea for post-
  cutover (do not silently add strict checking that breaks existing
  profiles).
- Coordination: `docker-compose.yml` and `docker/README.md` are shared
  files (also touched by nothing else in Phase 3, but T-004/T-005 read
  them) — additive service block only. Workspace `members` line in
  `src-tauri/Cargo.toml` as usual.
