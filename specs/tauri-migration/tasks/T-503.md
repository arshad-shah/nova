## Goal
The conversation orchestration loop ports to `verql-ai`: system-prompt
assembly from the same prompt files, the chars/4 token budget with the same
trim invariants, and the streaming tool-call loop emitting an
`AIStreamEvent` sequence indistinguishable from v1's — proven by replaying
recorded v1 streams with mocked providers.

## Acceptance criteria
- [ ] 1. History management parity: add_user_message / clear / set_messages
      (wholesale replace for conversation switch/branch) on
      `AIChatMessage {id, role system|user|assistant|tool, content,
      toolCalls?, toolCallId?, timestamp, isError?}` (shared/ai-types.ts,
      camelCase on the wire).
- [ ] 2. Prompt assembly: the `prompts/*.md` templates + fragments are carried
      **byte-identical** (embedded via include_str!) and
      `build_chat_system_prompt` interpolates the same slots (connection
      meta, schema context, plugin conversation context, connections summary,
      notifications summary, app-actions catalog); schema context is the
      cheap table-name list — first 200 names, `(+N more — call list_tables)`
      suffix, describe_table hint — never a full schema dump.
- [ ] 3. Token budget parity: `estimate_tokens = ceil(len/4)`;
      `estimate_message_tokens` adds tool-call name+arguments + 4 overhead;
      `trim_messages_to_budget` invariants — newest message always kept even
      if alone over budget, kept window advances to start on a `user` turn
      (never an orphaned tool result or leading assistant turn), fallback to
      last message if advancing consumes everything. Port the v1 unit tests
      (tests/unit/ai-token-estimate.test.ts) as Rust tests.
- [ ] 4. Budget wiring: DEFAULT_MAX_CONTEXT_TOKENS = 24000,
      MIN_HISTORY_TOKENS = 2000, per-round history budget
      `max(2000, max_context − estimate(system))`; the full history stays in
      memory for display/persistence — only the request payload is trimmed.
- [ ] 5. Tool loop parity: MAX_TOOL_ROUNDS = 10; per round the manager yields
      `tool-call` **before** executing; failure payloads pinned string-for-
      string — unknown tool `Unknown tool: <name>`, unparseable args
      `Failed to parse tool arguments`, blocked write `Blocked: this tool
      requires write access and the current permission profile is
      read-only.`, rejection `User rejected this action`; tool results
      recorded to history as role:tool messages with content
      `JSON.stringify({success, data})` / `{error: …}`; assistant message
      appended with its toolCalls; loop exits when a round makes no tool
      calls; terminal `done` carries summed usage or is omitted-usage when
      zero.
- [ ] 6. Approval integration seam: `needs_approval` → emit
      `approval-request` event `{requestId, toolName, toolDescription,
      parameters, display}` (display = description + ': ' + JSON params),
      publish to the attention hub (source 'ai', title 'AI action needs
      approval'), await resolution, attention resolved in all paths
      (uses T-504's manager — mock it here).
- [ ] 7. Abort parity: aborting stops the provider stream and the loop; no
      further events after abort except what v1 emitted (pin with a fixture).
- [ ] 8. Stream-replay parity: the corpus of recorded v1 `ai:chat:event`
      sequences (text-only chat; multi-round tool chat; blocked write;
      rejected approval; provider error) replays through the Rust loop with
      mocked providers producing **identical** event type/field/order
      sequences (per-case allowlist only for ids/timestamps).

## Notes
- The event *stream shape* is the contract (04-ipc): tool-call events never
  interleave wrongly with text deltas; `done` is terminal and emitted exactly
  once per chat() call. Chunk granularity of text deltas is allowlisted.
- v1 gotcha: `tool-result` for a *successful* execute uses `tool.name`
  as toolName, but the unknown-tool/parse-failure paths use
  `chunk.toolCall.name` — bug-for-bug parity, keep it.
- Recorded fixtures are generated from v1 `main` (golden rules,
  verification.md) — never authored by this task.
- Coordination: T-504 owns permission/approval internals; T-505 owns the
  channel wiring and broadcasts. This task must expose chat() as a stream the
  IPC layer forwards verbatim.
- `ai:chat:event` is a designated hot stream: it may be Channel-backed
  (`tauri::ipc::Channel`) per the ADR-0005 streaming addendum — the T-104
  shim keeps the renderer-facing `on()` shape and payloads exactly v1
  either way; record the mechanism decision in the Log.
