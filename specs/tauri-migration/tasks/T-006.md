## Goal
A written report answering, per platform, whether a Rust (non-Electron)
process can decrypt a real v1 `credentials.enc`, and an ADR-0007 amendment
fixing strategy (a) direct-decrypt / (b) v1.x export release / (c) re-enter
prompts for each OS. "Losing secrets silently is the only forbidden outcome"
— after this spike, T-203 and T-209 implement against decided facts, not
hope.

## Acceptance criteria
- [ ] 1. Report `specs/tauri-migration/spikes/T-006-secrets/report.md`
      documents the exact v1 on-disk format from the real code
      (`src/main/keyring.ts`): JSON map of `"<profileId>:<key>"` →
      base64(safeStorage ciphertext) or `"plain:" + base64(utf8)`, file
      mode 0600, written atomically; plus the composite-key namespace scheme
      (`__mcp__` etc.) that ADR-0007 preserves.
- [ ] 2. Per platform, answered with hands-on evidence (a PoC run or a
      precisely cited refusal), not from memory:
      (a) **Linux, `plain:` fallback** — decoded by a standalone process;
      round-trip demonstrated (trivial yes expected; prove it anyway);
      (b) **Linux, Secret Service-backed** — where Electron `safeStorage`
      keeps its key (Secret Service entry name, KDF, cipher) and whether a
      Rust process reading the same Secret Service entry can decrypt the
      blob;
      (c) **Windows (DPAPI)** — whether current-user-scope
      `CryptUnprotectData` from a different executable decrypts the v1
      blob, incl. any Chromium/Electron header prefix on the ciphertext;
      (d) **macOS (Keychain)** — whether the "verql Safe Storage"-style
      keychain item is readable by a differently-signed app (expected: ACL
      prompt or denial), and what that means in UX terms.
- [ ] 3. Platforms without hands-on access are marked "not exercised" with
      the best documentary evidence available — never presented as tested.
- [ ] 4. ADR-0007 gets an appended amendment: a per-platform table choosing
      a/b/c, and — if (b) is chosen anywhere — an explicit note that a
      final v1.x Electron "export for v2" release becomes a Phase 6
      dependency, escalated to the human owner.
- [ ] 5. The report also answers, for T-203: does the `keyring` crate's
      entry model support the planned `service="verql"`,
      `account="<namespace>/<key>"` scheme on all three platforms, and what
      happens headless (no Secret Service) — confirming or amending
      ADR-0007's fallback-file requirement.
- [ ] 6. Any PoC code is committed under the spike directory (throwaway
      quality acceptable there, and only there).

## Notes
- Generate fixtures by running v1 (`pnpm dev`) on each available platform
  and storing a secret; the fixture `credentials.enc` (with dummy secrets
  only — nothing real) may be committed to the spike dir.
- `retrieveSync` in v1 silently drops undecryptable entries (key rotation);
  the migration importer (T-209) must NOT copy that behavior — flag it in
  the report so T-209's spec inherits the warning.
- Touching ADR-0007 intersects nothing else in Phase 0 except T-001's broad
  glob — orchestrator serializes with T-001/T-002.
