## Goal
`verql-keyring` stores secrets in the OS credential store per ADR-0007
(`keyring` crate, `service = "verql"`, `account = "<namespace>/<key>"`), with
the encrypted-file fallback for Linux without Secret Service, and ports the
v1 `KeyringService` surface (`store/retrieve/retrieve_sync/has/delete/
delete_all/list_keys`), the profile-secret helpers (extract/inject/strip),
and the three gated `keyring:*` channels. Secrets never appear in
`config.json`, logs, or the activity stream.

## Acceptance criteria
- [ ] 1. Surface parity: all v1 `KeyringService` methods exist with the same
      semantics — `store_sync` with an empty value deletes the entry;
      `retrieve` of a missing key returns `None`; `list_keys(ns)` returns the
      key suffixes for that namespace; `delete_all(ns)` removes every entry
      for the namespace. Namespacing preserves the v1 `<profileId>:<key>`
      composite scheme mapped to `account = "<ns>/<key>"`.
- [ ] 2. Unrecoverable-entry parity: a stored value that can no longer be
      decrypted/read (fallback-file key rotated, keychain entry corrupt) is
      dropped and `None` returned — callers see a clean "missing key", never
      a repeating error (v1 `retrieveSync` catch-and-delete behavior).
- [ ] 3. Fallback store: when no OS backend is available, secrets go to an
      encrypted file (ChaCha20-Poly1305/age or Stronghold per ADR-0007 §2 —
      implementer's choice, recorded in the Log) written mode `0o600` via
      `atomic_write`; a one-time warning is logged; the fallback is never
      silently weaker than v1's documented `plain:` mode.
- [ ] 4. Hot-path cache: `retrieve_sync` is backed by a read-through cache
      invalidated on every `store`/`delete` (ADR-0007 consequences —
      per-entry OS calls would otherwise hammer the keychain on config load).
- [ ] 5. Profile-secret helpers ported behavior-identical from
      `profile-secrets.ts`: `extract_and_persist_secrets` stores each
      non-empty string secret field and blanks it to `""`;
      `strip_secrets_for_disk` derives the field set from
      `list_keys(profile.id)` (works when the original secret-key set is out
      of scope); `inject_secrets_from_keyring` restores all stored values;
      `delete_profile_secrets` awaits completion (no fire-and-forget).
- [ ] 6. Redaction helpers ported from `ipc/secrets.ts`:
      `SECRET_PLACEHOLDER = "__SECRET_PRESENT__"`; `redact_connection`
      replaces every non-empty secret field; `merge_incoming_profile` keeps
      the existing value when the incoming one is the placeholder, empty, or
      absent, and deletes the key when there is no existing value. The
      secret-field-key set is `{"password"}` ∪ driver-declared
      `type == "password"` fields, resolved through a `SecretFieldSource`
      seam (Phase 2 impl returns the static set incl. `sshPassword`-style
      fields once drivers register; T-301's registry implements the seam).
- [ ] 7. `keyring:*` gating parity (`ipc/keyring.ts`): reserved namespaces
      `__ai__` and `__mcp__` are rejected; the key must be a recognised
      connection-secret field; the profile id must exist in the config store.
      Error messages match v1 (`keyring: access to reserved namespace '<ns>'
      is not permitted`, etc.). All three checks run on store, retrieve, AND
      delete.
- [ ] 8. Adversarial cases (committed as tests): `keyring:retrieve` with
      `profileId = "__ai__"` fails; a secret value never appears in any
      activity entry or tracing output (assert against the T-206 recorder
      with a sentinel secret); contract fixtures for the three channels pass.

## Notes
- T-006's per-platform findings (which of ADR-0007 §3 a/b/c applies for
  *reading v1* `credentials.enc`) are input to T-209, not this task — this
  task owns the v2-native store only. Do not implement v1-file reading here.
- v1 AI keys are write-only by design: exposed via `ai:keys:set`/`ai:keys:has`
  (Phase 5), never via `keyring:retrieve`. Preserve that asymmetry.
- The `keyring` crate's OS backends behave differently under CI (headless
  Linux has no Secret Service): tests must run against the fallback store via
  an injected backend, not the real keychain.
- Coordination: one dispatch-table line per channel in
  `src-tauri/crates/verql-ipc/src/dispatch.rs` (shared file — add match arms
  only). `verql-config` (T-202) consumes this crate through its `SecretStore`
  trait; implement that trait here.
