## Goal
The native menu (macOS menu bar; accelerator table on every platform) is
built in Rust from a JSON serialization of `shared/menus.ts` — one source of
truth, as v1's hard-won comment block demands ("never edit one surface
alone"). Non-role items emit `menu:action`; accelerators resolve from the
user's live keybindings; a rebuild API exists for T-202 to call on
keybinding change.

## Acceptance criteria
- [ ] 1. `scripts/export-menus.mjs` serializes the `APP_MENUS` tree to
      `src-tauri/menus.json` (committed, regenerated deterministically):
      the full tree with `id`, resolved label text (run `t(labelKey)` at
      export time — the i18n catalogue is TS-only), `nativeRole`,
      `keybinding` action id, fixed `accelerator`, and the
      `surface`/`platform`/`devOnly` gates. A staleness check fails when
      `shared/menus.ts` changes without re-export (hash or regenerate+diff
      in CI/verify).
- [ ] 2. The Rust builder reimplements `menusFor('native', isMac, isDev)`
      semantics: surface/platform/devOnly gating and
      separator-trimming (`trimSeparators`) — unit-tested against fixture
      expectations exported from the TS side, so the two
      implementations cannot silently diverge.
- [ ] 3. All **31** `MENU_ACTION` ids (count them in `shared/menus.ts` —
      the inventory doc says 32; the source says 31, source wins) reach the
      renderer: non-role items become menu entries whose activation emits
      the `menu:action` event with the action id, exactly like v1's
      `webContents.send(IPC_EVENTS.MENU_ACTION, action)` — the renderer's
      `menuActions` registry (`menu-model.tsx`) runs UNMODIFIED.
- [ ] 4. `nativeRole` passthrough: v1's roles (`services`, `hide`,
      `hideOthers`, `unhide`, `quit`, `close`, `undo`, `redo`, `cut`,
      `copy`, `paste`, `selectAll`, `togglefullscreen`, `minimize`, `zoom`,
      `front`, `reload`, `toggleDevTools`) map to muda predefined items
      where one exists; roles muda lacks are implemented as emitted actions
      or window calls with a documented per-role mapping table in
      `menu.rs`. Items with a role AND an id (Edit menu) stay native on
      macOS.
- [ ] 5. Accelerator parity with `itemAccelerator`: fixed accelerators
      (`Cmd+,`, `CmdOrCtrl+Shift+N`, `CmdOrCtrl+Shift+T`, `CmdOrCtrl+F`,
      `Shift+Alt+F`) and keybinding-resolved ones
      (`resolveAccelerator`: pick the `Cmd`-prefixed variant on macOS,
      `Ctrl`-prefixed elsewhere, else first) — Electron accelerator syntax
      translated to muda syntax with a unit-tested conversion incl.
      `CmdOrCtrl`.
- [ ] 6. `rebuild_menu(keybindings)` API: given a new keybinding set,
      rebuilds the menu so accelerators move (v1: `settings:set` on
      `keybindings.*` → `buildAppMenu`). In Phase 1 it is exercised by a
      test/dev trigger; **T-202 wires it to `settings:set`** — leave the
      seam named and documented.
- [ ] 7. macOS app menu is labeled with the app name + ` (Dev)` in dev
      builds; there is no native About role — `about` routes through
      `menu:action` to the in-app `AboutModal` on every platform.

## Notes
- The Win/Linux **visible** bar stays the renderer's `MenuBar.tsx`
  (untouched); this task's Win/Linux deliverable is the accelerator table —
  on Tauri, menu accelerators only fire from a set application menu; if
  muda accelerators prove unreliable for a hidden-menu window, a
  renderer-side keydown fallback is a *finding to escalate*, not a silent
  substitution.
- Default keybindings live in `shared/settings.ts` (`KEYBINDING_ACTION`,
  10 actions); until T-202, build with defaults.
- `menu:action` payload is the bare action-id string (v1 sends a single
  arg) — the T-104 shim spreads event payloads; get the arity right.
- Touches `src-tauri/src/main.rs` (menu init) — serialize with T-105.
