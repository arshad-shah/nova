## Goal
A single cutover checklist exists that a human can walk top-to-bottom, with
every item backed by linked evidence (gate reports, artifacts, transcripts),
covering the 00-goals success criteria plus release mechanics — and the human
owner's recorded sign-off is the last entry before the final gate.

## Acceptance criteria
- [ ] 1. `specs/tauri-migration/cutover-checklist.md` exists with these
      sections, each item linking its evidence:
      **(a) Task graph** — every task in tasks/ is `done`; phase gate reports
      0–5 green and committed.
      **(b) Parity** — full suite green on all six drivers against seeded
      DBs, error-parity cases included (link: latest gate report + parity run
      transcript).
      **(c) Data migration** — verified from a real v1 install (config.json,
      credentials.enc, app.db) on macOS, Windows, AND Linux — per-OS
      transcript links; any secrets-migration caveats (ADR-0007/T-006) called
      out for release notes.
      **(d) Performance** — every guardrail at-or-better vs baseline-v1.md,
      or the accepting ADR linked (tests/parity/baseline-v2.md).
      **(e) Packaging** — installable artifacts verified: macOS dmg +
      rendered Homebrew cask, Windows package per the ADR-0008/T-604 outcome,
      Linux AppImage; artifact checksums + sizes listed.
      **(f) Decisions** — every ADR in decisions/ is status `accepted`
      (including amendments from spikes and T-604's ladder outcome).
      **(g) Release mechanics** — version/tag plan (scripts/release-tag.mjs /
      changesets), homebrew-bump workflow dry-run, Store submission status,
      docs site deployed, v2 What's New page live.
      **(h) Rollback plan** — last v1 release remains installable; the
      `v1-final` git tag (T-608) recorded; v2→v1 downgrade caveat documented
      (v1 cannot read data the v2 identifier dir now owns).
- [ ] 2. No checklist item is marked complete without a link to committed
      evidence — an adversarial reviewer spot-checks every link resolves and
      supports the claim.
- [ ] 3. Items the swarm could not verify (e.g. an OS with no runner, Store
      review pending) are explicitly listed as OPEN with what the human must
      do — the checklist never launders unknowns into checkmarks.
- [ ] 4. The human owner's sign-off (name/date/verdict, plus any accepted
      exceptions) is appended to the checklist and mirrored into this task's
      Log; per 00-goals, cutover cannot proceed without it.
- [ ] 5. T-699 consumes this checklist as its input: every checklist item
      maps 1:1 onto a final-gate check (no criteria exist only here or only
      there — cross-referenced by ids).

## Notes
- This is the migration's second explicit human touchpoint (the first was
  ADR ratification, T-001; T-604's ladder may have added a third). The task
  is `done` only after the sign-off entry exists — an orchestrator moving it
  to done without one violates the gate.
- Keep the checklist factual and diff-stable: it will be re-read at T-699 and
  likely by future audits; no marketing language.
- The rollback caveat matters: v2 imports v1 data by copy (T-209/T-605), so
  rolling back loses post-cutover work — say so plainly for release notes.
