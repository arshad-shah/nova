## Goal
A written report validating ADR-0008's amended ladder hands-on: primary
path (a) is the **officially documented EXE/MSI-linked Store listing**
(Tauri documents it; tauri-bundler has no native MSIX — versions-baseline);
this spike proves it works for Verql's existing listing, or determines
which lower rung applies. Finding this out now instead of at Phase 6 is
the entire point; T-604 implements the decided path.

## Acceptance criteria
- [ ] 1. The report confirms with evidence (a build attempt on Windows, or
      precisely cited current docs/issues if no Windows machine is
      available — marked as such): tauri-bundler still produces only
      NSIS/MSI (no native MSIX — issues #4818/#8548) at the version pinned
      by T-002, per the versions-baseline claim.
- [ ] 2. Primary rung (a) — **EXE/MSI-linked Store listing** — validated
      against Microsoft's and Tauri's current docs: the submission
      requirements are enumerated concretely — **code-signed installer**
      (real cert; v1's appx sidestepped this via Store signing — name the
      signing gap), silent-install flags, and the **offline WebView2
      installer** (`offlineInstaller` bundler mode) — and whether Verql's
      existing listing can be converted/updated to an EXE/MSI-linked one.
- [ ] 3. The identity question is answered concretely against v1's real
      Store identity from `package.json#build.appx`
      (`identityName: Arshadshah.verql`, `publisher:
      CN=2ABEC305-C7D9-4693-92FC-165FCE8EEA94`, `applicationId: Verql`):
      do Store users receive v2 as an update to the same listing on each
      rung, and does the appId change to `com.arshadshah.verql` (ADR-0008)
      interfere.
- [ ] 4. Option (b) is evaluated: third-party MSIX packaging over the Tauri
      build via `@choochmeque/tauri-windows-bundle` — can it carry the v1
      identity verbatim and pass Store validation (WACK), explicitly
      checking the known **WACK S-mode failure (tauri#14935)**.
- [ ] 5. The report recommends one rung — a/b/c — with consequences for the
      updater (Store-managed updates vs `verql-updater` channels) spelled
      out. Moving below rung (a) is explicitly framed as a **product
      decision requiring human sign-off** (ADR-0008 §1), and the ADR
      amendment records the owner's answer, not the swarm's.
- [ ] 6. ADR-0008 gets the appended amendment with the decided path and its
      Phase 6 implications for T-604.

## Notes
- v1 ships `win.target: "appx"` via electron-builder — the Store listing is
  live; breaking its update chain is a user-facing regression, which is why
  silent resolution is forbidden here.
- Signing posture: v1 macOS identity is `null` (unsigned dev builds); the
  Windows Store path has its own signing story (v1's appx: Store signs on
  ingestion; the EXE/MSI-linked path requires the developer's own code
  signing) — distinguish the two in the report; ADR-0008 §1 notes this
  makes the signing line load-bearing for rungs (a) and (b).
- Any test packaging artifacts stay in the spike dir or out of the repo;
  do not touch build config outside `specs/`.
