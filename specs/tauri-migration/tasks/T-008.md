## Goal
A written report resolving ADR-0008's front-loaded risk: can the Tauri build
produce a Microsoft-Store-acceptable MSIX carrying Verql's **existing** Store
identity, and if not, which rung of the fallback ladder applies. Finding this
out now instead of at Phase 6 is the entire point; T-604 implements the
decided path.

## Acceptance criteria
- [ ] 1. The report states, with evidence (a build attempt on Windows, or
      precisely cited current docs/issues if no Windows machine is
      available — marked as such): whether tauri-bundler produces MSIX
      today, and what it does produce (NSIS/MSI) at the version pinned by
      T-002.
- [ ] 2. If tauri-bundler cannot: evaluates ladder rung (a) — external MSIX
      packaging over the built binaries (`makeappx`+`signtool`, MSIX
      Packaging Tool, or msix-packaging tooling) — including whether the
      resulting package passes Store validation checks (WACK or documented
      equivalent) at least in principle.
- [ ] 3. The identity question is answered concretely against v1's real
      Store identity from `package.json#build.appx`
      (`identityName: Arshadshah.verql`, `publisher:
      CN=2ABEC305-C7D9-4693-92FC-165FCE8EEA94`, `applicationId: Verql`):
      can a Tauri-built package declare this identity so Store users
      receive v2 as an update to the same listing, and does the appId
      change to `com.arshadshah.verql` (ADR-0008) interfere.
- [ ] 4. Rung (b) is assessed: current Microsoft Store policy on Win32
      (EXE/MSI) app submission, and whether Verql's listing could move to
      it.
- [ ] 5. The report recommends one rung — a/b/c — with consequences for the
      updater (Store-managed updates vs `verql-updater` channels) spelled
      out. If the recommendation is (c) (defer Store at cutover, NSIS
      direct distribution), it is explicitly framed as a **product decision
      requiring human sign-off**, and the ADR amendment records the owner's
      answer, not the swarm's.
- [ ] 6. ADR-0008 gets the appended amendment with the decided path and its
      Phase 6 implications for T-604.

## Notes
- v1 ships `win.target: "appx"` via electron-builder — the Store listing is
  live; breaking its update chain is a user-facing regression, which is why
  silent resolution is forbidden here.
- Signing posture: v1 macOS identity is `null` (unsigned dev builds); the
  Windows Store path has its own signing story (Store signs on ingestion) —
  distinguish Store-signing from local signtool signing in the report.
- Any test packaging artifacts stay in the spike dir or out of the repo;
  do not touch build config outside `specs/`.
