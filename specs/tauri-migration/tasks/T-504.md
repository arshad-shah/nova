## Goal
The AI permission manager (profiles, per-tool overrides, approval lifecycle)
and the `perform_app_action` tool's correlated request/response round trip
port to `verql-ai`, using the shared write-detection from T-501 so AI and MCP
can never drift on "is this call a write".

## Acceptance criteria
- [ ] 1. Profiles `read-only | ask-write | auto` with v1 decision table:
      `is_write_blocked` true only for read-only × effective-write;
      `needs_approval` true only for ask-write × effective-write (auto never
      asks, read-only blocks instead of asking); effective write =
      `is_write_tool_call(override ?? tool.permission, params)` from
      verql-tools — the sql-content check included, so `explain_query`
      carrying `EXPLAIN ANALYZE DELETE …` or `SELECT 1; DROP …` prompts.
- [ ] 2. Per-tool overrides: set/remove override to read|write consulted
      before the declared permission.
- [ ] 3. Approval lifecycle parity, including edges: create returns a UUID and
      registers a pending entry with a no-op resolver; `wait_for_approval` on
      an unknown id resolves false immediately; `resolve_approval` on an
      unknown id is a no-op; resolving removes the entry (double-resolve
      safe); `has_pending_approval` reflects the map.
- [ ] 4. Profile persistence: read from `ai.permissionProfile` at startup
      (invalid values ignored, default ask-write), written on change —
      exposed to T-505's `ai:permission:get-profile`/`set-profile`.
- [ ] 5. App-action round trip parity (bundled/ai/internal/index.ts):
      `perform_app_action` registered with the exact v1 id, description,
      schema (`actionId` string, optional `params` record), permission read,
      `surfaces: ['ai']`; execute broadcasts `app:action:perform`
      `{requestId, actionId, params}` and awaits the correlated
      `app:action:result` `{requestId, success, error?}`; 10s timeout →
      `{success:false, display:'No response from the app (timed out)'}`;
      success → `data:{actionId}`, display = actionId; empty actionId →
      'No actionId provided'.
- [ ] 6. `app:action:result` handling resolves only its own requestId
      (concurrent actions don't cross-resolve — test with two in flight);
      disposal resolves all pending with 'Shutting down' and unregisters the
      tool.
- [ ] 7. Contract fixtures: `app:action:perform` event payload and the tool's
      result shapes diff clean against captured v1 payloads; the MCP server's
      exposed tool list (T-506) provably excludes `perform_app_action`
      (surfaces gate, asserted by an integration test here or in T-506 —
      state which in the Log).

## Notes
- The write-detection MUST be the shared verql-tools implementation — v1
  explicitly unified this after AI and MCP drifted (tool-schema.ts header);
  a reviewer finding a second regex here rejects the diff.
- The renderer's app-action registry enforces that only safe navigation
  actions run agentically — the backend does not re-validate actionId; parity
  means trusting the same seam (renderer code unchanged, non-goal).
- `app:action:result` is an `app:` domain channel whose plumbing landed in
  T-208; this task owns routing it to the pending-action map — coordinate,
  don't re-register the channel.
- Approval timeout: the AI loop has NO auto-timeout in v1 (the 5-minute
  timeout is MCP-only). Do not "add" one — a pending AI approval waits until
  the user answers or the stream aborts.
