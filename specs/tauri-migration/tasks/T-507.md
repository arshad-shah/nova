## Goal
A write tool call from an external MCP client blocks on user approval exactly
as in v1: renderer prompt + attention-hub announcement, approve/deny from the
renderer, and a hard 5-minute auto-deny — so a headless client can never
mutate a database without the user saying yes.

## Acceptance criteria
- [ ] 1. `needs_approval_for_call(tool, params) =
      is_write_tool_call(tool.permission, params)` — the shared verql-tools
      helper, no local reimplementation: write-permission tools always
      prompt, and read tools whose `sql` param is a write/DDL statement
      (`EXPLAIN ANALYZE DELETE …`, `SELECT 1; DROP …`) also prompt.
- [ ] 2. Approval request parity: UUID requestId; broadcast
      `mcp:approval-request` with `{requestId, toolId, toolName, sql
      (params.sql when string, else pretty-printed params JSON),
      permission}`; simultaneously published to the attention hub
      (kind 'approval', source 'mcp', title 'MCP query approval', body
      `<toolName>: <first 200 chars of sql>`).
- [ ] 3. Timeout parity: pending approvals auto-deny after exactly 5 minutes,
      resolving the attention request; a timed-out approval records activity
      status `rejected` and returns the client
      `Query rejected by user in Verql` (isError) — same as an explicit deny.
- [ ] 4. `mcp:approval-response` resolves the pending entry: approve →
      execute through the registry and return the result; deny → rejected
      text + `rejected` activity status; unknown/late requestId is a no-op;
      the attention request resolves in every path (approve/deny/timeout).
- [ ] 5. No-renderer edge: v1 auto-denies when no window exists. Pin the v2
      equivalent (no live renderer listener → deny) with a test, and record
      the exact condition in the Log.
- [ ] 6. Concurrency: multiple pending approvals resolve independently by
      requestId (test two in flight, resolve second-first).
- [ ] 7. e2e with a live MCP client: a write tool call (`query` with INSERT)
      surfaces the renderer prompt AND an OS notification (via T-508 when
      merged; attention-hub event otherwise), approve executes and the row
      lands; deny returns the rejection text; a second call left unanswered
      times out (test with a shortened injected timeout, constant pinned at
      5min in production code).

## Notes
- ADR-0006 makes this a first-class parity case: the Phase-5 gate (T-599)
  re-runs the live-client round trip; keep the e2e scripted and repeatable.
- The timeout must be injectable for tests but the production constant is
  5 * 60 * 1000 ms — a reviewer checks the wiring, not just the test.
- v1 removes the pending entry inside the timeout callback via
  `pendingApprovals.delete(requestId)` returning true — the delete-guard
  prevents double-resolution with a racing user response; replicate the
  race-safety (single consumer wins), e.g. with a oneshot channel.
- T-504 owns AI-side approvals (no timeout there); the shared piece is only
  the write-detection helper and the attention hub — don't merge the two
  managers.
