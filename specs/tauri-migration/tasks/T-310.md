## Goal
The cross-engine type-mapping glue and the two `migration:*` channels:
a `TypeMapperRegistry` drivers register their dialect translations into,
`map_type` with the v1 identity fallback, and `generate_migration_ddl`
delegating dialect-specific DDL to the target driver's capability — the
orchestrator never enumerates database types.

## Acceptance criteria
- [ ] 1. `TypeMapperRegistry` ports the SDK registry semantics: drivers
      register `(from, to, table, fallback)`; `resolve(from, to,
      source_type)` consults the exact-match table first, then the
      fallback fn; resolution is case-handled exactly as the v1 registry
      (verify against `type-mapper-registry.ts` and pin with tests).
- [ ] 2. `map_type` parity: a resolved mapping returns the registered
      `TypeMapping { source, target, lossy, note? }`; an unregistered
      direction returns identity with `lossy: true` and note exactly
      `No type mapper registered for <from> → <to>` (the renderer surfaces
      this string).
- [ ] 3. `generate_migration_ddl` parity: maps every column type via
      `map_type`, hands the mapped columns to the *target* driver's
      `generate_migration_ddl` capability, and returns `{ ddl, mappings }`.
      A target driver without the capability errors with exactly
      `Target driver '<to>' does not contribute generateMigrationDdl().
      Add it to the driver plugin's registration.`
- [ ] 4. Channels `migration:type-map(sourceType, from, to)` and
      `migration:generate-ddl(tableName, columns, from, to)` registered and
      passing contract round-trip fixtures (column input shape: name,
      dataType, nullable, isPrimaryKey, defaultValue).
- [ ] 5. Zero dialect knowledge in this task's code: no engine-name
      branches; mapping tables live in driver crates (T-303..T-305 register
      theirs) — unit tests here use fixture mappers, and one integration
      test with the real sqlite driver's registration proves the seam
      (`postgresql → sqlite` INTEGER PRIMARY KEY output matches the v1
      golden).

## Notes
- The identity fallback (criterion 2) is deliberate v1 design — "better
  than silently returning TEXT" — callers detect `lossy + note`. Don't
  substitute a cleverer default.
- The mapping *tables* (PG_TO_SQLITE, MYSQL_TO_PG, …) are driver-owned and
  ported by the driver tasks; if a driver task hasn't landed, its
  directions simply hit the fallback — that's correct interim behavior.
- Coordination: `src-tauri/crates/verql-db/src/type_map.rs` lives inside
  T-301's crate — T-310 depends on T-301, so no concurrent write, but add
  the module via a one-line `lib.rs` edit. Two dispatch-table lines in
  `src-tauri/crates/verql-ipc/src/dispatch.rs` (shared file).
