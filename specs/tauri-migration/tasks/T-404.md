## Goal
`verql-plugins` can parse, validate, and discover third-party plugin
manifests with v1's exact rules, classify v1 JS plugins as incompatible (per
ADR-0003 — reported, never silently dropped), and accept the v2 declarative
manifest (themes + connection fields, `sdkTarget` field, no executable code).

## Acceptance criteria
- [ ] 1. Manifest struct mirrors v1 `PluginManifest` (name, version,
      displayName, description, main, icon?, permissions?, contributes with
      all v1 contribution kinds) plus the ADR-0003 `sdkTarget` field; serde is
      permissive to unknown fields (v1 `JSON.parse` tolerated extras).
- [ ] 2. Validation parity with manifest-validation.ts, same order/messages in
      substance: name matches `^[a-z0-9-]+$`; version matches
      `^\d+\.\d+\.\d+(-[\w.]+)?(\+[\w.]+)?$`; displayName/description
      required; permissions must be an array of the six known capability
      strings with an actionable error listing the allowed set.
- [ ] 3. Per-contribution field checks ported exactly: drivers id+name;
      commands id+title; panels id+title+icon+location; connectionMiddleware
      id; connectionFields key+label+type; settings key+title+type; themes
      id+name+type∈{dark,light}; exporters id+name+extension; importers
      id+name+non-empty extensions; formatters id+name.
- [ ] 4. Classification (new, per ADR-0003): a manifest declaring executable
      code (`main` present/`.js`, or contribution kinds requiring code —
      drivers, commands, panels, middleware, exporters, importers,
      formatters) is classified `IncompatibleJs { name, displayName, version }`
      — kept in the plugin table with an error-like status naming ADR-0003,
      surfaced through `plugins:list` and consumed by T-605's report. A
      declarative manifest (themes and/or connectionFields + settings only,
      no `main`) is classified `Declarative` and proceeds.
- [ ] 5. Discovery parity: scans `<appData>/plugins/*` directories only;
      `plugin-manifest.json` preferred, `package.json` accepted only with the
      `verql-plugin` keyword; invalid JSON yields an error-state entry
      (phase `discover`) rather than a crash; unreadable entries skipped.
- [ ] 6. Bundled-name collision guard: a discovered plugin whose name matches
      a bundled (compiled-in) plugin name is refused with a warning — the
      bundled name list is exactly the v1 bundled set (verql-plugin-sqlite,
      -postgresql, -mysql, -mongodb, -redis, -snowflake, -db-tools, -ai,
      -core-formats, -core-themes, -ssh-tunnel, -os-notifications), so a
      third-party folder can never shadow a built-in driver.
- [ ] 7. Symlink walker parity: lstat-based (never follows links), depth
      capped at 32, returns the first symlink path or None; exported for the
      installer (T-405) and unit-tested with a symlinked fixture tree.
- [ ] 8. Unit tests port the intent of tests/unit/manifest-validation.test.ts
      plus new cases for `sdkTarget` and the IncompatibleJs classification.

## Notes
- v1's `main must end in .js` rule inverts in v2: `.js` main is what makes a
  plugin *incompatible*. Keep the v1 check available for classification so
  error messages stay truthful about *why* (ADR-0003 is the citation).
- v1's main-path traversal guard (resolve + prefix check pinning `main`
  inside the plugin dir) has no load path in v2 but the classification must
  not read/resolve `main` in a way that escapes the plugin dir.
- The lifecycle machinery (discover→validate→resolve→activate, degraded
  states, error budget) survives **only** for declarative plugins; bundled
  code is compiled in (ADR-0002) — do not port the JS activation phases.
- Coordination: T-405 (install) and T-407 (loading + channels) build directly
  on these types; `src-tauri/Cargo.toml` gains one member line.
