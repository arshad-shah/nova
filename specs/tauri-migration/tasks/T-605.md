## Goal
A v1 user launching v2 for the first time is offered a guided import of their
Electron-era data (T-209's `verql-migrate-v1` does the work), sees an honest
per-artifact report of what moved, and is told by name which installed JS
plugins cannot run in v2 (ADR-0003 §3) — nothing is silently dropped and the
v1 install is never mutated.

## Acceptance criteria
- [ ] 1. Detection: on startup with an empty/fresh v2 data dir, the v1
      Electron userData dir is located using T-209's per-OS locator (Electron
      app name `verql`): macOS `~/Library/Application Support/verql`, Windows
      `%APPDATA%\verql`, Linux `$XDG_CONFIG_HOME/verql` or `~/.config/verql`
      — necessary because the app identifier changed to `com.arshadshah.verql`
      (ADR-0008). Detection is read-only and tolerant of partial installs
      (config.json without app.db, etc.).
- [ ] 2. First-run flow: a migration screen offers Import / Skip before the
      normal onboarding; Import runs T-209's importer (config.json,
      credentials.enc secrets → OS keyring, app.db) with progress; Skip
      proceeds to a clean profile. The offer is recorded (appdata meta) so it
      is not re-shown every launch, and a manual re-run entry point exists
      (settings or command) for users who skipped.
- [ ] 3. Import report UI: per-artifact outcomes with counts — connections,
      settings, saved queries, query-history rows, open tabs, conversations
      (+messages), secrets migrated — and per-item failures listed with
      reasons (a failed secret or unreadable table degrades that item, never
      aborts the whole import silently). Report content matches
      verql-migrate-v1's returned summary 1:1. When the v1 config shows MCP
      was configured (`mcp.enabled` / a stored token), the report includes
      the **MCP client-reconfiguration notice** — the server now speaks
      Streamable HTTP at `/mcp` (legacy SSE endpoints not ported,
      ADR-0006) — with the new endpoint URL and a pointer to the settings
      MCP panel's copy-ready config (T-506).
- [ ] 4. Incompatible JS plugins: entries under v1
      `userData/plugins/` classified per T-404's IncompatibleJs rule are
      listed in the report by displayName + version with the "not compatible
      with v2" explanation per ADR-0003 §3; declarative-compatible plugins
      (themes/connectionFields-only) are offered for re-install/copy. Zero
      plugins → section omitted, not empty-rendered.
- [ ] 5. Source integrity: the entire flow never writes to the v1 directory
      (asserted in the e2e by hashing the v1 fixture tree before/after);
      re-running the import is idempotent on the v2 side (no duplicated
      history rows/conversations).
- [ ] 6. e2e against a real seeded v1 fixture install (a captured v1 userData
      tree committed as a parity fixture): detect → import → report contents
      asserted → app restarts with connections/settings/tabs/history/
      conversations live and a secret usable (test connection succeeds).
      Run on at least one OS here; all three OSes are verified by the final
      gate (00-goals requires macOS, Windows, Linux).
- [ ] 7. Renderer diff stays confined to the new migration components + its
      entry wiring (non-goal: no renderer redesign); strings go through the
      i18n catalogue.

## Notes
- T-209 built the importer + locator; this task builds the *UX and report*
  on top. If T-209's API lacks a structured per-artifact summary, that is a
  Log observation for the orchestrator (task-split rule), not a reason to
  fork import logic here.
- credentials.enc readability differs per platform/backend (T-006 spike +
  ADR-0007 amendments) — the report must distinguish "secret migrated" from
  "secret unreadable, re-enter password" honestly; the connection still
  imports with the secret stripped.
- The onboarding Welcome flow (docs/onboarding.md) already gates first-run
  screens; insert the migration step ahead of it rather than building a
  second first-run mechanism.
