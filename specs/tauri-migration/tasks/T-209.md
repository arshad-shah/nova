## Goal
A one-shot importer of v1 user data exists as a library crate: it locates the
v1 Electron `userData` directory per platform, imports `config.json`
(connections + settings), takes over `app.db`, and migrates secrets from
`credentials.enc` per the platform strategy T-006 recorded in ADR-0007 —
reporting, never silently losing, anything it cannot migrate. The Phase-6
first-run UX (T-605) is a thin caller of this crate.

## Acceptance criteria
- [ ] 1. Locator: finds the v1 userData dir for product name `Verql`
      (Electron conventions — macOS
      `~/Library/Application Support/Verql`, Windows `%APPDATA%/Verql`,
      Linux `$XDG_CONFIG_HOME/Verql` or `~/.config/Verql`), returns
      "not found" cleanly when absent, and never writes into it — the v1
      install stays intact and shippable (source files opened read-only;
      pinned by a test asserting v1 fixture dir is byte-identical after a
      full import).
- [ ] 2. Config import: parses v1 `config.json`, runs settings through
      `merge_with_defaults`, writes connections + settings through
      `verql-config`'s store (so secret-stripping and atomic-write rules
      apply). Unknown profile fields survive (open-map profiles).
- [ ] 3. app.db: copies the v1 `app.db` (plus `-wal`/`-shm` if present after
      a clean checkpoint) into the v2 data dir and opens it via
      `verql-appdata` — the v1 schema opens as-is (T-205 criterion); a
      corrupt copy follows T-205's quarantine path and is reported as a
      partial result, not a crash.
- [ ] 4. Secrets: parses `credentials.enc` (a JSON map of
      `"<namespace>:<key>"` → value, where values are either
      `plain:<base64>` or a base64 `safeStorage` ciphertext). `plain:`
      entries decode directly. Encrypted entries are handled per the
      platform strategy in ADR-0007 §3 as amended by T-006 (a: direct
      decrypt where the backing store is app-independent; b: v1 "export for
      v2" handoff file; c: re-entry prompt). Every migrated secret lands in
      `verql-keyring` under its original `<namespace>/<key>`.
- [ ] 5. The forbidden outcome is enforced in the result type: the importer
      returns a structured report listing, per profile and per namespace,
      which secrets migrated and which require re-entry (with the reason).
      There is no code path that drops a secret without a report entry —
      adversarial test: an undecryptable entry appears in the report, never
      vanishes.
- [ ] 6. Idempotence: running the import twice (or after a partial failure)
      does not duplicate connections, conversations, saved queries, history,
      or tabs — the importer records completion (per-section markers in the
      v2 side, e.g. appdata `meta`) and skips completed sections. v1's
      import primitives already no-op on non-empty tables; the config side
      needs its own guard.
- [ ] 7. Reserved namespaces migrate too: `__ai__` provider keys and the
      `__mcp__` token move to the keyring (they are exempt from the
      renderer-facing gating, which is IPC-level only — this is an internal
      caller).
- [ ] 8. Fixture-driven tests: a committed v1 userData fixture (config.json
      with 2+ profiles incl. secrets and unknown fields, credentials.enc
      with `plain:` entries, app.db at user_version 3 with rows in every
      table) imports fully on Linux CI; the resulting v2 stores serve
      identical `connections:list` (redacted) and `appdata:*` list responses.

## Notes
- `safeStorage`-encrypted entries cannot be unit-tested cross-platform;
  CI covers the `plain:` path and the report/laddering logic with an
  injected decryptor trait. Real per-platform decrypt verification is a
  Phase-6 gate item (00-goals success criteria), driven by T-006's ADR
  amendment — read that amendment before implementing strategy (a).
- The `plain:` prefix check is load-bearing: `:` never appears in base64,
  so an untagged value is always ciphertext (v1 `keyring.ts` comment).
- Do not build UI here — T-605 owns the first-run UX. This crate is
  library + report types only.
- Coordination: workspace `members` line in `src-tauri/Cargo.toml` is
  shared with every crate-creating task.
