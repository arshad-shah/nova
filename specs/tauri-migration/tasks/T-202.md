## Goal
`verql-config` owns `config.json` (connections + settings) with the exact v1
`ConfigStore` behavior: atomic writes, prototype-pollution-style key-path
guards, secret stripping on every save, change listeners — plus the four
`settings:*` channels in `verql-ipc`, the `settings:changed` broadcast, and
the keybinding→menu-rebuild hook. A v1 `config.json` round-trips unchanged
(modulo key order).

## Acceptance criteria
- [ ] 1. Load parity: a missing or unparseable `config.json` yields
      `{ connections: [], settings: defaults }` (never a crash); parsed
      settings go through `merge_with_defaults` (T-201); connections default
      to `[]`. On load, keyring-backed secrets are injected into the
      in-memory profiles (via the secret-store seam, see Notes).
- [ ] 2. Save parity: every save serializes with 2-space-indented JSON and
      runs each connection through the strip-for-disk chokepoint so
      keyring-backed fields are blanked (`""`) — including saves triggered by
      unrelated settings changes (the v1 leak guard in `store.ts` `save()`).
      Writes go through `verql-core::atomic_write`. Adversarial test: after a
      profile with a password is saved and then any setting is changed, the
      on-disk file contains no plaintext secret.
- [ ] 3. Key-path guards: `set_setting`/`get_setting` split on `.`, rejecting
      segments `__proto__`/`constructor`/`prototype` and empty segments with
      the v1 error message shape (`Settings key path '<p>' contains forbidden
      segment '<s>'`). Rust has no prototype chain, but the wire behavior
      (rejection + message) is contract and stays.
- [ ] 4. `set_setting` semantics: intermediate objects auto-created when
      `undefined`; a non-object intermediate errors with the v1 message
      (`Cannot set '<p>': intermediate '<q>' is not an object (got <t>)`);
      an unchanged value (`Object.is` equivalent) skips the write AND skips
      listener notification; `reset_category` restores the category default,
      saves, and notifies with the category key + full category value.
- [ ] 5. `settings:get-all` returns settings with `ai.openaiKey`/
      `ai.anthropicKey` redacted to `""`; `settings:get` on category `ai`
      applies the same redaction (port `redactSettings`/`redactAi`).
- [ ] 6. `settings:set` routes `ai.openaiKey`/`ai.anthropicKey` into the
      keyring under namespace `__ai__` (keys `openai`/`anthropic`) and does
      NOT write them to config or broadcast; all other paths write the store,
      then broadcast `settings:changed(keyPath, value)` — after the store has
      durably written (v1 ordering, pinned by a test). `settings:reset`
      broadcasts `(category, updatedCategoryValue)` and returns the value.
- [ ] 7. Menu rebuild hook: when the key path is `keybindings` or starts with
      `keybindings.`, `settings:set`/`settings:reset` trigger the T-106 menu
      rebuild with the current `keybindings` category (seam function; unit
      test asserts it fires exactly for those paths).
- [ ] 8. Contract fixtures for all four `settings:*` channels round-trip
      byte-stably; a captured v1 `config.json` fixture loads and re-saves to
      semantically identical JSON (key order excepted).

## Notes
- Secret seam: v1 `ConfigStore` takes a `KeyringLike` (with a no-op fallback).
  Mirror that as a `SecretStore` trait defined in this crate with a no-op
  impl; T-203's `verql-keyring` provides the real one plus the
  extract/inject/strip helpers. Do not implement keyring logic here.
- `setSetting` is the renderer's high-frequency path; the unchanged-value
  short-circuit (criterion 4) is a real perf guard, not an optimization nicety.
- Coordination: registering `settings:*` in the dispatch table edits
  `src-tauri/crates/verql-ipc/src/dispatch.rs` — a file every handler task
  touches one line of. Add only your four match arms; rebase conflicts there
  are expected and mechanical.
- `settings:changed` is also consumed by v1 renderer logic that assumes
  post-write ordering (04-ipc §event-stream parity).
