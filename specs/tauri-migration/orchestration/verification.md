# Verification — parity gates and the test matrix

Adversarial review catches what reading finds; verification catches what only
*running* finds. Nothing merges on review alone. This file defines the
standing per-merge gate, the phase gates, and the parity harness that anchors
"the Rust port behaves like the Electron original" in executable checks
instead of vibes.

## Ground rules

- Verification is **evidence-based**: a verifier reports commands, exit
  codes, and output excerpts. "Tests pass" without the transcript is not a
  verification.
- The Electron app on `main` is the **behavioral oracle** for the whole
  migration. When a parity question comes up, the answer is "run the v1 code
  path and look", not "read the v1 code and guess" — the old test-db stack
  (`scripts/test-dbs.sh`) exists precisely so both stacks can be run against
  identical seeded databases.
- Tests written by an implementer are reviewed by the same adversarial panel
  as the code. A test that asserts the bug is worse than no test.

## Standing per-merge gate

Run by the verifier on every merge candidate, after rebase onto `v2-tauri`,
scoped by what the task touches:

| Scope (from the task's `verify.scope`) | Commands |
|---|---|
| `rust` | `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace` |
| `renderer` | `pnpm typecheck`, `pnpm test -- --run` (unit project), affected story tests |
| `contract` (IPC/bindings changes) | regenerate bindings, `git diff --exit-code` on generated files, contract round-trip tests |
| `e2e` (tasks that claim user-visible behavior) | the task's listed driver/e2e scenario against the seeded test DBs |

Plus, always: the task's own `verify` commands, verbatim.

Keep the standing gate under ~10 minutes; anything slower belongs in the
phase gate, or the merge queue stalls the swarm.

## The parity harness (built in Phase 1, used forever)

A task early in the migration builds `tests/parity/`: a harness that drives
**the same operation through both stacks** and diffs the serialized results.

- **Fixture databases**: the seeded Postgres/MySQL/Mongo/Redis containers
  from `docker-compose.yml` + the seeded SQLite file
  (`scripts/make-sqlite-testdb.sh`). Both stacks connect to identical data.
- **Golden files**: for each parity case (a query, an introspection call, an
  export, an error scenario), the v1 Electron main process is driven
  headlessly to produce a golden JSON result committed under
  `tests/parity/golden/`. The Rust side must reproduce it field-for-field
  (modulo an explicit, per-case allowlist of permitted differences — e.g.
  duration fields — recorded next to the golden, never globally).
- **Error parity matters as much as success parity**: wrong password, dead
  host, syntax error, constraint violation, timeout — each driver's parity
  suite includes the failure cases, asserting the `DbErrorCode`
  classification and the user-visible message shape survive the port.
- Golden files are regenerated only from v1 (`main`), never edited by hand,
  and never regenerated by the same task that makes them pass.

Every driver task, the config-store task, the export/import tasks, and the
keyring task list specific parity cases in their acceptance criteria.

## Phase gates

Run by a dedicated verifier agent when a phase's last task merges — and
periodically mid-phase (playbook §hygiene). A phase does not open until the
previous phase's gate is green and its results are committed to the
integration branch under `specs/tauri-migration/tasks/gate-reports/`.

Every gate includes: full `rust` + `renderer` standing gates over the whole
workspace, the complete parity suite implemented so far, and a **smoke
matrix** — the app builds and boots via `cargo tauri build`/`dev` on the
platforms available to the swarm (document which were actually run; do not
claim platforms that weren't).

Additional per-phase exit criteria live in
[`../02-migration-strategy.md`](../02-migration-strategy.md) — that document
owns *what* each phase must prove; this one owns *how* proof is produced and
recorded.

## Performance guardrails

Tauri is partly a performance/footprint play; verify it instead of assuming
it. The phase gate from Phase 3 onward records, against the seeded DBs:

- cold start to interactive window (ms),
- 100k-row query result: execution → grid-rendered (ms) and peak RSS,
- bundle/installer size per platform,

compared against the same numbers measured once on v1 (recorded in
`tests/parity/baseline-v1.md` by the harness task). Regressions vs v1 on any
of these are gate failures unless an ADR explicitly accepts them.

## What verification does not do

- It does not fix. A verifier's diff footprint is zero (gate reports are
  committed by the orchestrator).
- It does not reinterpret criteria. Ambiguity in a `verify` command is
  reported as a task-spec defect.
- It does not skip "unrelated" failures on the integration branch: a red
  standing gate on `v2-tauri` freezes the merge queue until a fix task lands,
  because every queued candidate would otherwise rebase onto a broken base.
